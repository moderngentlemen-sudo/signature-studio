# Signature Studio 2.0: Product, UX and Technical Proposal

Status: **v1, 2026-10-08.** The owner told us to build a new application from the specification rather than port the original. Section 7 records what this release implements and what still needs approval.

---

## A. Product redesign proposal

### What Signature Studio 2.0 is

Signature Studio 2.0 is a focused workspace for designing an email signature and getting it into Gmail correctly. It is built on four ideas:

1. **One document, two outputs.** Each project is a single structured design document. The Full signature and the Reply signature are both rendered from it, and visibility badges control which components appear in which. Nothing is duplicated.
2. **One renderer.** The editor canvas displays the *actual email HTML*, generated by the same pure function that produces the copied and exported signature. Interaction handles (selection, resize, drop indicators) sit in an overlay above it. A control that does not change the exported signature cannot exist, because the canvas *is* the export.
3. **Images are only "ready" once they are published and verified.** Every image that appears in a variant is processed into an email derivative, hashed, published to a public immutable host, and then fetched back anonymously. Only after that check passes can the variant be copied or installed. The built-in Modern Gentlemen logo and the social icons go through the same pipeline as user uploads.
4. **Progressive disclosure, not two editors.** Simple Mode and Advanced Mode are two views of the same editor and document. Simple Mode is a guided rail: Profile → Look → Logo & photo → Socials → Install. Advanced Mode adds the component library, layer tree, full inspector, and document controls. Switching modes changes which panels are shown and never changes the document.

### What makes it better than a typical signature builder

| Problem in typical tools | 2.0 answer |
|---|---|
| The preview looks right, but Gmail shows broken images | Publish-and-verify pipeline; copying is blocked until images are verified |
| Editor styles silently differ from the export | The canvas renders the export HTML itself |
| Maintaining separate Full and Reply signatures | One master document with per-component visibility (Both / Full / Reply / Hidden) |
| Switching templates destroys custom work | Templates are *layouts* applied over a persistent profile, socials and assets. Custom blocks are kept or explicitly dropped, and every apply can be undone in one step |
| Webfonts that never reach recipients | Each font declares an email fallback, and a "As recipients see it" preview renders with fallbacks only |
| Rounded or circular images that break in Outlook | Shape, crop and zoom are baked into the hosted PNG derivative |
| Absolute-positioned designs that fall apart in email | A flow layout model (stacks, rows, columns) that maps one-to-one onto table-based email HTML |

### Positioning

The product should feel like a premium design tool. Visually it is quiet, typographic and ink-on-paper, with a single brass accent. It should not look like an admin dashboard.

## B. Interface proposal

### Workspace layout

```
┌──────────────────────────────────────────────────────────────────────────┐
│ ◆ Project ▾   Simple | Advanced     ↶ ↷    [ Full | Reply | Compare ]  ⊕ Zoom   Preview   Export ▾   [ Install in Gmail ] │
├────────────┬────────────────────────────────────────────┬────────────────┤
│ Rail       │                                            │ Inspector      │
│ ─ Templates│              Signature canvas              │ (contextual)   │
│ ─ Add      │      (real email HTML + overlay handles)    │ Content        │
│ ─ Layers   │                                            │ Typography     │
│ ─ Profile  │                                            │ Layout         │
│ ─ Brand    │      ──────────── target width ruler ────── │ Visibility     │
│ ─ Assets   │                                            │                │
├────────────┴────────────────────────────────────────────┴────────────────┤
│ Status: width 512/600px · 3 images ready · saved locally                 │
└──────────────────────────────────────────────────────────────────────────┘
```

* **Top bar:** project menu, the mode switch, undo and redo, the Full / Reply / Compare switch, zoom, Preview, Export, and the primary *Install in Gmail* button.
* **Left rail:** Templates, Add (component library), Layers, Profile, Brand (palette, fonts, saved kits) and Assets. Simple Mode replaces the rail with the guided steps.
* **Canvas:** click to select. Double-click text to edit it in place. Drag to move. Drag image corners to resize, drag a block's right edge to set its width, and drag column gutters to set column ratios. Snapping uses a 4px grid and sibling widths, and Alt disables snapping for fine adjustment. Dashed drop indicators show where a dragged item will land. Click outside to deselect.
* **Inspector:** grouped into Content, Text, Box, Layout and Visibility, and shows only what applies to the selected component. With nothing selected it shows the document settings: width, scale, palette, fonts, spacing and Auto-Fit.
* **Status bar:** live width against the target, overflow warnings, image readiness and save state.

### Simple Mode (3–5 minutes)

1. **Start.** Choose a template, or let the profession picker suggest one.
2. **Profile.** One form for name, title, company and contacts. Every connected component updates live.
3. **Look.** Palette and typography presets shown as large visual swatches, plus a layout switcher.
4. **Logo & photo.** Upload, then crop, zoom and shape in one dialog. Alt text is suggested automatically.
5. **Socials.** Paste URLs and the platform is detected automatically. Choose an icon style.
6. **Install.** Opens the Gmail wizard.

### Advanced Mode

This mode adds the component library (click or drag to insert), the layer tree (rename, reorder by drag or keyboard, group and ungroup, lock, hide, visibility badges), the full typography and box controls, saved components, brand kits, and export settings.

### Gmail installation wizard

1. **Readiness:** a per-image checklist (Ready / Preparing / Needs attention / Could not prepare / Not used in this variant) with Retry, Replace and Remove actions.
2. **Copy Full**, then step-by-step instructions to paste it into Gmail → Settings → Signature → *Create new*.
3. **Copy Reply**, the same steps again.
4. **Defaults:** shows exactly where to set "For new emails use: Full" and "On reply/forward use: Reply", including the per-address selector when the account has several send-as addresses. Users who want one signature for both contexts get a shortcut path.
5. **Verify:** a checklist that walks the user through sending a test email to themselves, and explains that installed signatures do not update automatically when the project changes.

Copying always puts *rich* HTML on the clipboard (`text/html` plus a `text/plain` fallback), never source code. Copying the source is a separate advanced option.

### Template browser

The browser has search, category chips, favourites and recently used templates, and renders each preview live with your own profile ("See it with my details"). Applying a template shows a non-modal summary of what is kept, what is replaced, and which custom blocks will be kept in an "Extras" section, and the apply can always be undone.

### Responsive behaviour

On narrow screens the rail and inspector become bottom sheets. Mobile is designed for editing the profile and content, previewing, and copying. Precision layout is aimed at tablet and desktop.

## C. Technical architecture proposal

### Stack

| Concern | Choice | Why |
|---|---|---|
| App | **React 19 + TypeScript + Vite** | Mainstream, fast to build, and a large talent pool. No SSR is needed for an editor |
| State | **Zustand + Immer** | A single store with immutable snapshots makes undo and redo straightforward and cheap through structural sharing |
| Styling | Hand-written CSS with design tokens (custom properties) | Full control over a premium visual language, with no utility noise in an editor-heavy UI |
| Icons (UI) | lucide-react | Consistent, tree-shakeable icons |
| Validation | **zod** | Versioned project schema validation for import and migration |
| Local storage | **IndexedDB** (idb-keyval) | Projects and image blobs stored locally with no account required |
| PNG export | html-to-image | Rasterises the same email DOM at 2× resolution |
| QR | qrcode-generator | Pure client-side, with no third-party service |
| Tests | **Vitest** (unit and DOM) + **Playwright** (end-to-end) | Fast unit coverage plus real-browser interaction tests |

### Document model (schema v1)

```ts
Project {
  schema: "signature-studio.project", version: 1,
  id, name, createdAt, updatedAt, templateId?,
  profile: { fields: {fullName, displayName, title, company, department, pronouns,
             phone, mobile, email, website, address, tagline, intro, booking},
             custom: [{id, label, value}],
             socials: [{id, platform, url, label?, visible}] },
  theme: { colors: {ink, muted, accent, link, surface, rule},
           fonts: {display, body}, size, lineHeight, width, scale, align, background },
  root: StackNode,            // the layout tree
  assets: { [id]: AssetMeta } // blobs live in IndexedDB, keyed by id
  published: { [hash]: {url, verifiedAt, bytes, width, height} }
}
Node = { id, type, name?, visibility: "both"|"full"|"reply"|"hidden", locked?,
         box?: {padX, padY, bg, border, radius, width, align}, text?: TextStyle, props }
type ∈ stack | row | column | field | text | contact | image | social | button |
       divider | spacer | qr | badge
```

* **Connected fields:** a `field` node references a profile key, such as `{field: "title"}`. Detaching copies the current value into the node's own `text` and sets `detached: true`. Reattaching is offered from the inspector.
* **Theme tokens:** colours such as `$ink` and `$accent` and fonts such as `$display` and `$body` resolve at render time. A component can either inherit a token or override it.
* **Library components** are presets of these 13 node types (for example Name = `field(fullName)` with display text style, and Booking = `button` linked to the `booking` field). That keeps the renderer small while covering all 24+ library entries.

### Rendering

`renderEmail(project, { variant, mode, resolveImage })` is one pure function that returns table-based HTML with inline CSS.

* `mode: "edit"` adds `data-ss-id` attributes and renders ghosts for nodes hidden in the current variant. The canvas displays it inside a **Shadow DOM** so app CSS cannot leak in.
* `mode: "email"` emits clean output with no attributes, no scripts, no classes and no `<style>` blocks. It is validated by `validateEmailHtml()`, which rejects `data:`, `blob:`, relative or non-HTTPS image sources, `javascript:` links, and any script.
* `resolveImage` is the only difference between the two modes. The editor resolves object URLs, while export resolves verified public URLs and *fails* if any image is unresolved.

### Image pipeline

`prepareVariant(project, variant)`:

1. Collect the image requirements actually present in the variant: uploads, built-in artwork, social icons (rendered from bundled SVGs in the chosen colour and style) and QR codes.
2. Rasterise each one at 2× its display size with crop, zoom, shape and radius baked in, as PNG (or JPEG for large photos).
3. Compute a SHA-256 hash of the final bytes. The object key is `s/<hash>.<ext>`, which contains no personal data and is immutable.
4. If `published[hash]` exists and was verified recently, reuse it. Otherwise upload through the **AssetHost** adapter.
5. **Verify** with an anonymous `fetch` (`credentials: "omit"`, `cache: "no-store"`): the response must be HTTPS and 200, have an `image/*` content type, and decode with `createImageBitmap` to the expected dimensions.
6. Render the final HTML with the verified URLs, then run the validator. Only then are Copy, Install and HTML download enabled.

### Hosting recommendation

The recommended host is **Cloudflare R2 behind a small Worker on a custom domain** (for example `img.signature.studio`).

* **No inactivity pausing.** This addresses the paused-Supabase failure mode the specification describes.
* **Zero egress fees** and low storage costs. A signature PNG is roughly 5–40 KB.
* **Immutable, content-addressed URLs** under a domain we own, so the backing store can migrate later without breaking signatures already sent.
* The Worker validates magic bytes (PNG, JPEG or GIF only), a 1 MB maximum size, and that the uploaded body hashes to the claimed key. It sends `Cache-Control: public, max-age=31536000, immutable` and `Access-Control-Allow-Origin: *`. It never fetches remote URLs, so there is no SSRF risk.
* Upload authorisation: before accounts exist, the deployment uses a bearer token. Once accounts exist, uploads require a signed-in session token. Reads are public.
* **Source assets stay private:** originals stay in IndexedDB (and later in private cloud storage). Only email derivatives are published, and only after the user consents ("Images in your signature will be publicly accessible at a permanent link so recipients can see them").

The `AssetHost` interface also lets an organisation plug in its own endpoint. A local development host (`npm run dev:host`) exists for testing. The verifier labels it "Not publicly reachable", so it can never produce a false "Ready".

### Persistence

* **Local (this release):** IndexedDB stores projects, image blobs, saved components and brand kits, with debounced autosave, crash recovery, project list, rename, duplicate, delete, and JSON import and export (image sources embedded) with schema migration.
* **Cloud (Phase 5, awaiting approval):** Supabase Auth (magic link, Google sign-in and passkeys) with Postgres and row-level security. Concretely:
  * a `projects` table with a `revision` integer and **optimistic concurrency** (`update … where revision = $expected`); a mismatch opens a conflict dialog instead of overwriting;
  * a `project_revisions` table for named versions and restore;
  * private source assets in storage, with email derivatives still on R2.

  This keeps Postgres for what it is good at, and the email-critical images do not depend on it.

### Gmail integration

* **This release:** the guided copy-and-paste wizard, which is fully supported and works with every Gmail account type.
* **Future, awaiting approval:** optional OAuth one-click install through `users.settings.sendAs.patch` (the `signature` field). Caveats:
  * It needs the `gmail.settings.basic` scope, which Google classifies as restricted. That means app verification and possibly a third-party security assessment, with recurring cost.
  * It can only write the send-as signature. It cannot create Gmail's named signatures or set the separate new-email and reply defaults, so the wizard is still needed for Full/Reply defaults.
  * We will not use undocumented endpoints.

### Migration

A versioned `migrate(raw) → Project` chain is built into the importer. Legacy formats from the original application are **not** imported in this release because the owner directed a clean build. Phase 5 can add a one-way importer for the old Block/Design formats. It would be reviewed against real exports and would never touch the production database.

### Testing

* Unit tests cover tree operations, visibility, the renderer and the HTML validator, template application (content preservation), history coalescing, Auto-Fit, URL sanitisation, social detection and migration.
* Playwright end-to-end tests cover onboarding, editing, Full/Reply switching, undo, insertion, export and import.
* Live Gmail acceptance tests cannot be automated honestly. A manual protocol is documented in `docs/GMAIL_ACCEPTANCE.md`, and the results are recorded only when actually performed.

### Deployment

The application is a static SPA, deployable to Cloudflare Pages, Vercel or Netlify. The `worker/` directory contains the image host. Rollback means redeploying a previous immutable build. Published images are never deleted by deploys.
